# APP-SPEC — Веб-приложение «Финансы + Склад» для менеджера маркетплейса (MVP)

> Статус: спека MVP, согласована по 9 решениям (Q1–Q9).
> Дата: 2026-07-01. Площадка MVP: **Wildberries**. Пользователь: финансовый менеджер магазина.
> Источник модели: рабочая Google-таблица менеджера (8 вкладок, WB P&L-движок) —
> `docs.google.com/spreadsheets/d/1g4awujdIiRabTBzIpR-U5qX5hnAmKNzB0OKKAcAkS4I`

---

## 1. Цель и контекст

Дать менеджеру/селлеру **рабочий инструмент сразу** и докручивать на практике. Приложение
заменяет ручную Google-таблицу: тянет данные **по API маркетплейса** (начинаем с WB),
считает P&L и склад автоматически, показывает утренний дашборд «что заработали / что горит /
что дозаказать».

Менеджер новый, опыта мало — поэтому инструмент должен **считать сам** и **не врать молча**
(подсвечивать дыры в данных). Со временем приложение становится единым UI поверх уже
существующей автоматизации SellerAI (MCP-серверы `wb-mcp`/`ozon-mcp`/`ym-mcp`, агенты L1/L2).

## 2. Границы MVP

**В MVP (сейчас):**
- Финансовый контур (P&L) по WB — на данных API.
- Складской контур (остатки, оборачиваемость, дозаказ, неликвиды).
- Себестоимость (ручной ввод + импорт из таблицы).
- Переменные/постоянные расходы (реклама авто + ручные).
- Калькулятор рентабельности акций.
- Дашборд + гарантии по данным (сверка/полнота/аудит).

**Вне MVP (дорожная карта v2+, §12):** управление рекламой, отзывы, SEO/контент,
ценообразование, воронка, прогноз спроса; подключение Ozon/ЯМ.

## 3. Архитектура данных (ключевой принцип)

Разделяем два слоя — это лечит хрупкость исходной таблицы (живой пересчёт → #REF!):

- **Сырьё (raw):** снимки из API. **Неизменяемые.** Закрытая неделя фиксируется навсегда,
  копится как история. Пересчёт прошлых периодов запрещён.
- **Витрина (derived):** расчёты P&L/склада поверх сырья. Пересчитывается свободно.

Модель **marketplace-agnostic**: у каждой сущности поле `marketplace` (`wb` | `ozon` | `ym`).
WB реализуем целиком; Ozon/ЯМ добавляются адаптерами позже без переписывания ядра.

## 4. Источники данных (WB API) и частоты

| Данные | Источник (API / MCP) | Частота | Куда идёт |
|---|---|---|---|
| **Отчёт о реализации** | `reportDetailByPeriod` / `wb_get_realization_report` | **раз в неделю**, авто после публикации отчёта WB (вт-ср за прошлую неделю) | ядро P&L (было: лист «Отчет Wb») |
| Остатки FBO/FBS | `/api/v1/supplier/stocks` / `wb_get_inventory` | раз в день | модуль «Склад» |
| Заказы / продажи | `wb_get_orders` / `wb_get_sales` | раз в день | оперативный дашборд, скорость продаж |
| Реклама (расход, ДРР) | Advert API / `wb_get_campaign_stats` | раз в день | строка «Реклама» переменных расходов |
| Цены | `wb_get_prices` | по запросу / раз в день | калькулятор акций |
| Баланс / выплаты | `wb_get_balance` / `wb_get_payments` | раз в неделю | сверка «к перечислению vs факт» |

Плюс кнопка **«Обновить сейчас»** для ручного дёрга любого источника.

Отчёт реализации — «золотой источник» (по нему WB реально платит). В нём уже лежит почти весь
P&L: продажи, возвраты, комиссия, логистика, хранение, штрафы, удержания, доплаты,
к перечислению, % выкупа. Из API **нельзя** получить только **себестоимость** (§6).

## 5. Модель P&L (витрина)

Повторяет логику листов «Формулы» → «Прибыль» → «Сводка», но на данных API. Считается по
SKU и агрегируется на период (неделя / месяц):

```
Выручка (продажи со скидкой WB)
− Возвраты
= Чистая выручка
− Комиссия WB
− Логистика (прямая + обратная)
− Хранение (платное хранение WB — из отчёта реализации)
− Платная приёмка
− Штрафы / Прочие удержания
+ Доплаты
= К перечислению продавцу        ← сверяется с фактическим поступлением (§10)
− Себестоимость проданного (Σ SKU × cost)     [§6]
= Валовая прибыль
− Переменные расходы (реклама/самовыкупы)      [§7]
− Постоянные расходы (менеджер/контент/склад)  [§7]
− Налог: УСН 6% «Доходы». База = сумма продаж покупателям (полная цена реализации), НЕ «к перечислению». Комиссию WB на «Доходах» из базы вычитать нельзя. (В листе «Формулы» уже так: налог от «согласованной розничной цены продажи».)
= ЧИСТАЯ ПРИБЫЛЬ БИЗНЕСА
Метрики: Маржинальность = Чистая прибыль / Выручка;  ROI = Чистая прибыль / Себестоимость
Доля в доходе (ABC: A/B/C) — как в «Формулы»
% выкупа = 1 − Возвраты/Продажи
```

Каждая строка хранит источник (какой отчёт/эндпоинт) для аудит-следа.

## 6. Себестоимость

- Привязана к **SKU** (баркод / артикул продавца) — как лист «Для заполнения», кол. K.
- Ввод: **(1)** вручную в карточке товара; **(2)** массовый **импорт из Google-таблицы/Excel**
  (первичная загрузка и обновление пачкой).
- Состав: **полностью готовое изделие** = сырьё/материалы + упаковка + доп. расходы. Без комиссий
  и логистики WB. Одна цифра на SKU, как «Себестоимость позиции (без WB)» в «Формулы».
- Новый SKU из API без себестоимости → флаг «нет себестоимости», подсветка; P&L по нему помечается
  как неточный (не врёт молча).
- v2: разбивка на компоненты, партии закупа по разной цене (FIFO).

## 7. Расходы сверх отчёта WB

Превращают «валовую прибыль по WB» в честную «чистую прибыль бизнеса». Пустой блок «ПЕРЕМЕННЫЕ
РАСХОДЫ» из «Сводки» (Самовыкупы/Реклама/Менеджер/Контент/Склад):

| Расход | Ввод | Тип |
|---|---|---|
| Реклама (ДРР) | 🔌 авто из API рекламы, аллокация на предмет/SKU | переменный |
| Самовыкупы | ✍️ ручной | **пока не ведутся — строка скрыта по умолчанию** (включаемая) |
| Менеджер (ФОТ) | ✍️ ручной, **повторяющийся** (напр. 50 000 ₽/мес) | постоянный |
| Контент | ✍️ ручной за период | периодический |
| Склад (внешний FBS) | ✍️ ручной, повторяющийся | постоянный |

Постоянные расходы вводятся один раз с флагом «повторять каждый месяц». **Платное хранение WB
не дублируем** — оно уже в отчёте реализации; строка «Склад» = **один внешний склад (работает
только по FBS)**, вносим его аренду/содержание, если платный.

## 8. Модуль «Склад» (нового раздела в таблице не было — создаём)

На данных `wb_get_inventory` + скорость продаж из `wb_get_sales`. Модель работы — **только FBS
с одного внешнего склада**, поэтому остатки = собственный склад (FBS), а дозаказ/оборачиваемость
считаются под своё производство/закуп (не под поставки на FBO WB):

- Остатки по SKU (FBS), актуальные.
- **Скорость продаж** — среднее в день за 14/30 дней.
- **На сколько дней хватит** (days of supply) = остаток / скорость.
- 🔴 **Алерт «скоро закончится»** — остаток **< 14 дней** (порог настраиваемый, с учётом срока
  пополнения) → «дозаказать столько-то».
- 🟡 **Неликвиды** — большой остаток + низкая скорость → замороженные деньги = остаток × cost.
- **Деньги на складе** — Σ остатков по себестоимости.
- Оборачиваемость по норме < 60 дней.
- v2: поставки / товар в пути / приёмка, прогноз спроса под сезон.

## 9. Калькулятор рентабельности акций

Повторяет «Отчет для акции» + «Участие в акции»: вводим условия акции (срок, скидка, снижение
комиссии, штраф за неучастие) → считаем плановую цену, комиссию при участии, **чистую прибыль и
рентабельность**, вердикт **участвовать / нет** по каждому SKU. Текущую розницу берём из
`wb_get_prices`.

## 10. Гарантии по данным (доверие)

1. 🔴 **Сверка с фактом:** «К перечислению» из отчёта ↔ фактическое поступление
   (`wb_get_balance`/`wb_get_payments`). Показываем расхождение.
2. **Полнота:** подсветка дыр — период без загруженного отчёта, SKU без себестоимости, реклама не
   подтянулась. Модель **не врёт молча**.
3. **Неизменяемость** закрытых недель (§3).
4. **Аудит-след:** у каждой цифры виден источник (отчёт/эндпоинт) — можно ткнуть и проверить.

## 13. Открытые вопросы

**Решено (2026-07-01):**
- ✅ **Себестоимость** = полностью готовое изделие (сырьё + упаковка + доп. расходы), без комиссий/логистики WB.
- ✅ **Налог** — УСН 6% «Доходы»; база = сумма продаж покупателям (не «к перечислению»).
- ✅ **Самовыкупы** — пока не ведутся (строка скрыта, включаемая).
- ✅ **Внешний склад** — один, работает только по FBS.

**Осталось уточнить на этапе разработки:**
- **Аренда/содержание внешнего склада** — платный ли он и на какую сумму (иначе строка «Склад» = 0).
- **Точные поля отчёта реализации** — сверить имена колонок API против листа «Отчет Wb».
- **Нюанс СПП в базе налога** — фиксировать доход по фактической цене продажи покупателю (для акций/СПП уточнить у бухгалтера).

## 15. Стек и каркас MVP

Решения: **single-tenant**, деплой **Timeweb RU**, очереди на **Redis с самого старта**, WB-клиент
по **вашим OpenAPI-спекам**, тема фронта — из репозитория `webkoth`.

**Стек (выровнен под `webkoth` — переиспользуем тему и компоненты):**

| Слой | Выбор |
|---|---|
| Язык | TypeScript сквозной |
| Фреймворк | Next.js 16 (App Router, RSC) + React 19 |
| Стили / UI | Tailwind v4 (без конфига, `@theme` в CSS) + shadcn/ui (style `base-vega`, baseColor `mist`, Base UI) + lucide |
| **Тема** | **Webkoth Theme** — shadcn-registry из `webkoth` (`public/r/theme.json` + `theme-provider.json`): коралловый OKLCH primary, light/dark, палитра-переключатель, фон «соты», токены `chart-1..5`. Витрина: `webkoth/app/ui-kit/page.tsx` |
| Графики | shadcn `chart` (Recharts) — цвета из токенов темы `chart-1..5` |
| Тёмная тема | next-themes |
| Бэк (API) | Next Route Handlers |
| Воркер синка | отдельный Node-процесс |
| Очереди | **BullMQ + Redis** (с самого старта) — джобы синка, ретраи, расписание |
| БД | PostgreSQL + Prisma |
| Auth | Auth.js (credentials), single-tenant |
| WB-клиент | по **OpenAPI-спекам** `docs/api-reference/openapi/wildberries` (+ логика из `mcp/wb-mcp`) |
| Деплой | Timeweb RU (tw-deploy) |

**Подключение темы:** копируем `components.json` из `webkoth` (style `base-vega`, mist, Tailwind v4),
затем переносим registry-элементы темы — токены в `app/globals.css` (из `public/r/theme.json`) и
`components/theme-provider.tsx` (из `theme-provider.json`). Дашборд собираем компонентами shadcn —
цвета KPI и графиков берутся из темы автоматически.

**Раскладка (monorepo, pnpm workspaces):**

```
apps/
  web/            # Next.js 16 — дашборд + API routes (тема из webkoth)
  worker/         # BullMQ-воркеры: недельный отчёт + ежедневные остатки/реклама/заказы
packages/
  db/             # Prisma schema (§14) + миграции
  wb-client/      # WB API по OpenAPI-спекам (+ логика из mcp/wb-mcp)
  core/           # витрина: P&L, склад, ABC, сверки — чистые функции, покрыты тестами
  shared/         # типы, константы (пороги 14д/60д, ставка УСН 6%)
docker-compose.yml # postgres + redis
```

**План по фазам (маппинг на разделы):**

- **Ф0 — Скелет.** Монорепо, Docker (postgres+redis), Prisma init, Next.js + тема из `webkoth`
  («hello dashboard» уже в фирменных цветах), BullMQ+Redis подключены, Auth.js один пользователь, `.env`.
- **Ф1 — Слой сырья (§3, §4, §14).** Модели `Product/RealizationReport(+Line)/StockSnapshot/AdSpend/Payout`;
  `wb-client` по OpenAPI; BullMQ-джобы (недельный отчёт **immutable** + ежедневные); «Обновить сейчас».
  *Готово: в БД реальная неделя из WB.*
- **Ф2 — Себестоимость и расходы (§6, §7).** `CostPrice` (ручной + импорт CSV/Excel из его таблицы),
  `Expense` (повторяющиеся); флаг «нет себестоимости».
- **Ф3 — Витрина P&L (§5, §10).** `core`: waterfall, налог УСН 6% от продаж, ABC, %выкупа, ROI;
  `PeriodSummary`; сверка «к перечислению vs `Payout`». *Готово: цифры бьются с его «Прибылью».*
- **Ф4 — Склад (§8).** Скорость, days-of-supply, алерты <14д, дозаказ, неликвиды, деньги на складе (FBS).
- **Ф5 — Дашборд (§11).** Экран из спеки на shadcn-charts: waterfall → алерты → склад/топы → график → калькулятор акций (§9).
- **Ф6 — Гарантии и полировка (§10).** Подсветка неполноты, аудит-след, badges «нет себестоимости».

**Критерий готовности MVP:** цифры приложения за конкретную неделю **сходятся с Google-таблицей** менеджера за ту же неделю.
